# Fallout34 변환기 업데이트 후 한글 원본 ESM 오류 조사

## 목적과 범위

사용자의 Fallout 3 또는 New Vegas 원본 ESM·ESP에 이미 한글이 적용된 상태에서 Fallout34 변환기가 실패하거나 변환 결과의 한글이 깨지는 경우를 다룬다. **Fallout34 변환기**와 **이 저장소의 한글 패처**는 별도 프로그램이다. 먼저 어느 단계에서 오류가 났는지 구분한다. 이 문서는 새 버전에서 자동으로 패치가 안전하다는 보증이 아니다.

## 1. 증상과 입력 확인

1. 설치기·변환기 버전과 설치 방식, FO3/FNV 중 실패한 게임, 오류가 난 단계와 최신 전체 로그를 확인한다. 화면에 마지막으로 나온 오류만 보지 말고 최초 traceback과 그 앞의 실패를 찾는다. 후속 Havok 오류가 다른 최초 오류를 가릴 수 있다.
2. 사용자의 원본 게임 폴더 및 활성 ESM·ESP 목록, 원본이 영문인지 한글인지, 백업이나 MO2의 가상 파일이 사용되는지 확인한다. 실제 사용 파일과 시험 파일을 구분하고 경로와 해시를 기록한다. 원본 ESM, 게임 Data, 세이브를 덮어쓰지 않는다.
3. `UnicodeDecodeError`의 인코딩·바이트·함수와 `UnicodeEncodeError`, `?`·`�` 등 손상 여부를 각각 확인한다. 한국어 UTF-8 바이트를 CP1252로 읽는 문제는 한 가지 가능성일 뿐, 모든 변환 실패의 원인으로 단정하지 않는다. 도구 오류, 스크립트 오류, 입력 파일 차이도 별도로 조사한다.
4. 원본 설치기 실행 파일의 실제 버전과 SHA-256을 기록한다. 예: `Get-FileHash -Algorithm SHA256 -LiteralPath 'C:\path\to\payload\app\f34conv.exe'`. 파일을 실행하거나 수정하기 전에 사용자 제공 설치기와 출력 경로를 확인한다. 바이너리나 로그를 외부에 공개할 때 사용자 경로·개인 정보를 확인한다.

## 2. 최소 재현과 도구 경로

- 기존 설치본이 아닌 **별도 작업 폴더**에 시험 설치기와 출력·캐시를 마련한다. 먼저 변환기 도움말과 `--dry-run`으로 이 버전의 옵션과 실제 입력·출력 경로를 확인한다. `--install`이나 전체 설치를 시험이라고 가정하지 않는다.
- 가능한 경우 FO3와 FNV를 각각 `plugin` 단계만, `--no-install` 또는 동등한 옵션으로 실행한다. 예전 0.9.148에서는 `build.py fo3 --only plugin --variant <시험명>`이 별도 variant에 쓰고, 실제 실행 계획은 `--dry-run`으로 확인할 수 있었다. 버전마다 옵션과 경로가 달라질 수 있다.
- 실행 환경에 지정한 게임의 `F34_SOURCE_DATA`와 FO3/FNV 원본 Data 경로, FO4 Data 경로가 맞는지 실제 플러그인 목록까지 확인한다. 특히 FNV 시험에서 FO3 경로가 함께 있으면 잘못된 게임 목록이 선택되지 않았는지 확인한다. 시험 결과가 어느 입력·버전에서 나왔는지 기록한다.
- FFmpeg와 **해당 설치기에 동봉된 최신 DirectXTex texconv**의 실제 경로를 확인하고 필요한 환경 변수로 명시한다. PATH의 오래된 DirectX SDK `texconv`는 전혀 다른 CLI일 수 있다. 0.9.148 시험에서는 이 문제로 후반 텍스처 단계가 실패했으며 `payload/bin/texconv.exe`로 재시험했다. 새 설치기에 해당 파일이 없으면 실제 동봉 경로와 `--help`를 먼저 확인한다.
- 각 게임의 종료 코드, 최초 실패·후속 오류, 로그 및 산출물 경로를 기록한다. 하나의 로그에서만 실패 메시지가 안 보인다는 사실을 전체 설치 성공으로 해석하지 않는다.

## 3. 수정 방법 선택

공식 소스나 공식 수정이 사용 가능하면 우선 확인한다. 소스 수정이 가능할 때는 **사람에게 표시되는 텍스트 필드에 한해** UTF-8 strict를 먼저 시도하고 실패하면 원래 CP1252로 읽는 방식을 검토한다. 출력 인코딩과 각 호출 경로도 함께 살핀다. EDID·파일 경로·바이너리·숫자 필드에 일괄 인코딩 변환을 적용하지 않는다. 원본 인코딩이 혼재하거나 바이트만으로 구분되지 않는 경우를 검증한다.

공식 코드가 없는 컴파일된 실행 파일이고 별도 시험이 필요하다면:

1. 새로운 버전의 **사용자 소유 실행 파일**을 기준으로 함수와 호출 맥락을 다시 조사한다. 0.9.102와 0.9.148의 파일 해시와 상수 위치는 서로 다르다. 이름이 같은 문자열이 있다는 이유만으로 동일 함수라고 판단하지 않는다.
2. 입력 디코딩, 출력 인코딩, FO3 설정 등 실제로 실패하거나 손상을 일으키는 지점을 각각 확인한다. 수정 대상의 함수 맥락·원본 패턴·출현 횟수·동일 길이를 검증하고, 정확한 원본 SHA-256 이외에는 거부하는 **버전 전용 도구**를 만든다. 패턴이 없거나 중복되면 실패시키고 원본을 유지한다.
3. 항상 별도의 새 경로에만 시험 실행 파일을 생성하고 기존 파일을 덮어쓰지 않는다. 원본·수정본 해시와 바뀐 바이트 및 범위를 기록한다. 수정한 실행 파일이나 공식 설치기 전체는 저장소·배포본에 포함하지 않는다.
4. 과거 실험의 `cp1252` → 동일 길이의 `utf-8 ` 치환은 **UTF-8 우선/CP1252 폴백이 아니다**. 원래 CP1252인 문자열이 실패하거나 손상될 수 있고, 다른 읽기·쓰기 경로도 남는다. 해시나 앵커 검사를 우회해 다른 버전에 사용하지 않는다.

기존 예시: [0.9.102 시험](INSTALLER_09102_UTF8_TRIAL.md), [0.9.148 시험](INSTALLER_09148_UTF8_TRIAL.md). 이 파일과 `tools/patch_fallout34_09102_utf8.py`, `tools/patch_fallout34_09148_utf8.py`는 과거 조사 근거이지 새 빌드용 범용 패치가 아니다.

## 4. 검증과 번역 패처 연계

1. 새 실행 파일의 성공 사례뿐 아니라 잘못된 해시, 누락·중복 앵커, 입력과 출력이 같은 경로, 기존 출력 파일에 대한 거부도 자동 시험한다. 패치 전후 파일 길이와 의도한 바이트 외 변경이 없는지 검사한다.
2. 사용자 보유 입력을 읽는 별도 출력에서 FO3·FNV 플러그인 단계를 각각 재실행한다. 종료 코드와 최초 traceback을 확인하고 FFmpeg·texconv 오류를 문자 인코딩 문제와 구분한다. 전체 설치나 인게임 시험을 하지 않았다면 그렇게 명시한다.
3. 생성 ESM의 레코드와 GRUP 경계, 압축 및 참조 구조를 검사한다. 한글 텍스트와 이름·대사·설정 등 사용자가 볼 수 있는 여러 레코드 유형을 원본과 비교해 깨진 글자, 잘못된 인코딩과 예상치 못한 변경을 조사한다. 입력이 영문인 경우와 CP1252 특수문자가 있는 경우도 가능한 범위에서 시험한다. 표본 개수와 확인 범위를 적고 완역이나 전체 보존을 추정하지 않는다.
4. 이 저장소의 한글 패처를 새 ESM에 적용할 때는 FormID·종류·EditorID·필드 순번과 원문 지문을 확인한다. 변경되거나 사라진 항목을 무조건 덮어쓰지 않는다. 입력과 출력의 레코드·그룹 구조와 LAND 바이트 해시를 비교하고, 미일치 수량을 실제 미번역 수량으로 단정하지 않는다. 새 문구와 별도 ESP·MCM 등은 따로 확인한다.
5. 관련 회귀 테스트와 `python -m unittest discover -s tests`를 실행한다. 설치기 배포본을 만들 경우 번들에 번역 데이터가 들어갔는지, 독립 실행 파일과 SHA-256을 확인한다. 새 버전·설정 조합 전체가 검증된 것으로 표시하지 않는다.

## 5. 결과 기록

버전, 실행 파일 해시, 입력 종류와 테스트 경로, 원인과 근거, 실제 수정한 위치, 재현 명령과 도구 경로, 각 게임의 종료 코드, 데이터·지형·문자 검증 결과, 남은 오류와 미검증 범위를 버전별 문서에 남긴다. 공식 수정이 나왔는지와 실험 수정이 그 버전에 불필요해졌는지도 확인한다. GitHub 업로드·정식 배포는 사용자가 요청한 범위에 따라 별도로 진행한다.
